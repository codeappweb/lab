# Architecture — 20K Article Experiment (codeappweb/lab)

## Purpose

Controlled experiment: can Google organically discover, crawl and index a large
GitHub Pages static site WITHOUT Search Console, manual submission, indexing
APIs, verification meta or artificial pings?

Experiment conditions (enforced by policy, verified by audit):
- Google Search Console: NOT CONNECTED
- Sitemap submission: NONE (sitemap is published at its standard location only)
- Google Indexing API / third-party submission: NONE
- `<meta name="google-site-verification">`: NONE
- `noindex`: never added to real content

## Stack

- Jekyll on GitHub Pages, branch build from `main`, baseurl `/lab/`
- Permalink scheme: posts `/:title/`, categories `/danh-muc/<parent>/` and `/danh-muc/<parent>/<child>/`
- Content: Markdown posts in `_posts/`, editorial pages in `danh-muc/`, hub pages `/hub/c01..c12/` (noindex)
- No frontend frameworks; vanilla HTML/CSS/JS only

## Taxonomy

- `data/taxonomy.yml`: 12 parent categories (P01–P12), 98 children
- Parent category pages: indexable, long editorial content (validator requires ≥200 words, warns below 1600)
- Child category pages: `noindex: true` stubs except fully written ones (e.g. `chan-doan-loi`)
- `data/article-manifest.jsonl`: planned topic queue (single source of truth for topics)
- `data/topic-queue.json`: generated view of open topics (never hand-edited)

## Sitemap architecture

Replaces the `jekyll-sitemap` plugin with deterministic static XML generated by
`scripts/gen-sitemap-shards.mjs`:

- `sitemap.xml` — sitemap index (absolute URLs, `/lab/` base)
- `sitemaps/articles-NNN.xml` — ~1000 article URLs per shard, zero-padded
- `sitemaps/categories.xml` — indexable category pages only (noindex/hub excluded)
- `sitemaps/static.xml` — main pages from `data/navigation.yml`
- `data/sitemap-shards.json` — deterministic shard metadata (no timestamps → diff only on content change)

`robots.txt` points to the absolute sitemap index URL:
`https://codeappweb.github.io/lab/sitemap.xml`.

## Article schema

See `docs/SCHEMA-ARTICLE.md`. New articles carry full structured metadata in
front matter (id, primary_keyword, search_intent, category, subcategory,
entities, related_articles, created_at, updated_at, freshness_status,
legal_sensitivity). The 22 legacy C05 articles are exempt (flagged legacy).

## Pipeline (GitHub Actions: `.github/workflows/content-pipeline.yml`)

Daily 02:00 UTC + manual dispatch. Concurrency group `production-pipeline`,
`cancel-in-progress: false` (never two publishing jobs at once).

Steps: content quality → duplicate detection → link check → sitemap
regeneration → sitemap validation → self-heal audit → legal freshness → SEO
scoring → content hashes → manifest sync → topic queue → dashboard → Jekyll
smoke build → commit-if-diff. Validation failure = no commit, no deploy change
(production keeps the previous Pages build).

Deployment itself is the GitHub Pages branch build; this workflow only gates
what lands on `main`.

## Reports (all generated, none hand-edited except google-discovery.json)

- `reports/self-heal-audit.json` — CRITICAL/HIGH/MEDIUM/LOW issues
- `reports/legal-freshness.json` — legal-sensitive article verification status
- `reports/seo-scores.json` — internal quality metric (NOT a Google score)
- `reports/content-hashes.json` — SHA-256 per post body (change detection)
- `reports/dashboard.md` — local experiment dashboard
- `reports/google-discovery.json` — MANUAL observation log (UNKNOWN /
  NOT_OBSERVED / OBSERVED). Never fabricated; `site:` counts are never treated
  as exact index totals.

## Scale control

- Target: 20,000 articles, but never mass-generated. Quality first.
- Progression: 100 → 500 → 1000 → ... only when all gates stay green.
- GitHub Pages limit ~1 GB; current output is far below. `gen-dashboard.mjs`
  tracks page counts; before each batch expansion the projected size must stay
  safely below 1 GB, otherwise expansion STOPS and the issue is reported.
- Compact HTML, globally shared CSS/JS/assets — no per-article asset copies.

## Batch protocol

Every batch = one traceable commit (`content: publish batch NNN`). AI authors
must run `node scripts/validate-deploy.mjs` equivalent gates before pushing;
CI re-validates and never deploys broken changes.
